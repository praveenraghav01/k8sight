Overview

A native desktop & web UI for Kubernetes — no CLI required.

k8sight is a fast Kubernetes management app: a native desktop build for macOS, Windows and Linux, plus a Docker image you can run anywhere. It reads your kubeconfig and gives you a live dashboard, resource browsing and editing, topology, logs, an in-pod terminal, ArgoCD, and one-click cloud onboarding — all without leaving the app.

Highlights

  • One-click cloud clusters — import AWS EKS, Azure AKS and Google GKE straight from your account, with no aws/az/gcloud CLI required, at import or runtime.
  • Live cluster overview — node/pod health, workload charts, capacity, and per-container status.
  • Full resource management — browse, search, edit YAML, scale, restart and delete across all common kinds, with cross-links (namespace → node → pod → owner).
  • Topology, ArgoCD, Helm, Custom Resources — interactive graphs and GitOps views.
  • Logs, in-pod shell, port-forward — a real TTY over WebSocket, a pro log viewer, and one-click port forwarding.
  • Bring your own AI — a built-in read-only assistant (any OpenAI-compatible LLM), docked coding agents (Claude Code, Copilot, Gemini, Codex, opencode), and an MCP server so agents can drive the cluster.
  • Command palette (⌘K), light/dark themes, and a native title bar.

New here? Install k8sight, then jump to your cloud: AWS, Azure, or GKE. For local clusters (Docker Desktop, kind, minikube), see Local & other.

Install

Desktop app, Docker, or run from source.

Desktop app (recommended)

Download the build for your OS from the downloads section or the GitHub releases page — macOS (Apple Silicon & Intel), Windows and Linux. It bundles everything it needs; open it and it reads your ~/.kube/config.

Docker

Run the published image and mount your kubeconfig. Publishing to 127.0.0.1 keeps the API off your network (see Security):

docker run --rm -p 127.0.0.1:8080:3001 \
  -v "$HOME/.kube:/home/node/.kube:ro" \
  praveenraghav/k8s-manager-ui:latest

Then open http://localhost:8080.

From source

git clone https://github.com/praveenraghav01/k8sight
cd k8sight
npm install && (cd client && npm install)
npm run build
npm start          # http://localhost:3001

Prerequisites: Node 18+. A local kubectl/helm is optional — used only for a few features (Helm, CRDs, ArgoCD, the in-pod shell); core browsing talks to the API server directly.

Running k8sight

Desktop, single-port web server, or Docker.
  • Desktop app — launch it like any app; it runs the backend internally and serves the UI. Best for local clusters that listen on 127.0.0.1.
  • Web (single port) — npm start serves the built UI + API on http://localhost:3001.
  • Dev (hot reload) — npm run dev runs the API on 3001 and Vite on 3000 (which proxies /api and /ws).
  • Docker — see Install; the image bundles Node, kubectl and kubelogin.

k8sight reads the kubeconfig at KUBECONFIG or ~/.kube/config, and you switch the active cluster from the context picker, the ⌘K palette, or a pinned rail. By default the backend binds loopback only — see Security.

AWS EKS

Connect your Amazon EKS clusters — no aws CLI required.

k8sight imports Amazon EKS clusters with no aws CLI required. It's built on the AWS SDK, so sign-in, discovery, and even auth-token generation run in-process. There is nothing for a maintainer to register — you sign in with your own AWS identity.

AWS SSO (IAM Identity Center) Recommended

Enter your start URL (e.g. https://my-org.awsapps.com/start) or pick an existing profile; k8sight runs the device-authorization flow, then lets you choose an account + role.

Access keys (IAM user)

An access key id + secret (and optional session token).

Assume-role

A role ARN plus a source profile.

k8sight then discovers every EKS cluster across your accounts and regions and writes the ones you pick into your kubeconfig. Cluster auth is generated natively (the bundled eks-token.js signs an STS request), so using the clusters needs no aws binary either.

Use it

Preferences → Cloud Integrations → Add AWS clusters, or the Add AWS button in the context dropdown.

  1. Pick a method:
    • AWS SSO → enter your start URL → approve the device code in the browser → choose account + role.
    • Access key → paste the key id / secret (open Advanced options).
    • IAM role → enter the role ARN + source profile (open Advanced options).
  2. k8sight lists your EKS clusters across regions.
  3. Select clusters → Add → they're written to your kubeconfig.

An Add AWS option also appears on the "couldn't connect" screen for quick re-auth.

Permissions you need

Two separate layers — both are required:

1. AWS IAM (to discover + import):

  • eks:ListClusters and eks:DescribeCluster on the target regions/accounts.
  • sts:GetCallerIdentity (always allowed) — used to mint the auth token.
  • For SSO: permission to list your assigned accounts/roles (handled by Identity Center).

2. Kubernetes access on the cluster (to actually use it): ⚠️ the classic EKS gotcha

Your IAM principal (user or assumed role) must be mapped to a Kubernetes group, or you'll authenticate but get Unauthorized / forbidden. Do this on the cluster with either:

  • an EKS access entry (recommended, newer): aws eks create-access-entry + an access policy (e.g. AmazonEKSClusterAdminPolicy), or the console's Access tab; or
  • the legacy aws-auth ConfigMap in kube-system, mapping your ARN to system:masters (or a custom group with RBAC).

If a cluster imports but every request is forbidden, this RBAC mapping is what's missing — the #1 EKS issue.

How auth works

  • Sign-in and discovery use the AWS SDK for JavaScript v3 (EKS, STS, SSO/SSO-OIDC clients) — no aws binary.
  • Access keys / assume-role sign-ins are saved as an ~/.aws profile so the token helper can read them at runtime; SSO role credentials are saved as a short-lived profile.
  • The kubeconfig user runs an exec plugin: eks-token.js --cluster <name> --region <region>, a drop-in for aws eks get-token. It presigns an STS GetCallerIdentity request (with the x-k8s-aws-id header) and returns it as the k8s-aws-v1. bearer token EKS expects. Tokens are short-lived; clients refresh automatically.

Troubleshooting

  • Cluster imports, but everything is forbidden / Unauthorized → your IAM principal isn't mapped to Kubernetes RBAC. Add an EKS access entry or an aws-auth mapping (see permissions above).
  • No clusters found → check the region(s), and that the identity has eks:ListClusters. SSO: confirm you picked an account/role that can see the clusters.
  • SSO device code expired / "session expired" → re-run the SSO sign-in; tokens are short-lived.
  • Assume-role fails → verify the role's trust policy allows your source profile/principal and that the source profile is valid.
  • Wrong account → for SSO, pick a different account/role in the picker; for keys, use the correct key pair.

Azure AKS

Connect your Azure AKS clusters — no az CLI required.

k8sight imports Azure AKS clusters with no az CLI required (though you can use it if you prefer). There is nothing for a maintainer to register — the browser flow reuses the Azure CLI's well-known public client id, so it works with no setup.

Browser Recommended

Azure AD authorization-code + PKCE in your system browser, then the Azure Resource Manager (ARM) REST API. Because sign-in happens in your real browser, it carries your device's compliance state, so it works with managed-device Conditional Access policies.

Azure CLI (az)

If az is installed and you're already logged in (az login), k8sight can drive it instead. Useful if the browser flow is blocked.

Either way k8sight discovers every AKS cluster you can access across all subscriptions and writes the ones you pick into your kubeconfig.

Use it

Preferences → Cloud Integrations → Add Azure clusters, or the Add Azure button in the context dropdown.

  1. Click Sign in with browser (or Use the Azure CLI if you prefer).
  2. Pick your account and complete sign-in in the browser.
  3. k8sight lists your AKS clusters across all subscriptions.
  4. Select clusters → Add → they're written to your kubeconfig and appear in the context switcher.

An Add Azure option also appears on the "couldn't connect" screen, so an expired Azure session is one click from re-auth.

Permissions you need

The signed-in identity needs, per the clusters you want:

  • List clusters: Reader (or any role that can read AKS resources) on the subscription(s) / resource group(s).
  • Get user credentials (default): the Azure Kubernetes Service Cluster User Role on the cluster. Returns a normal, AAD-aware kubeconfig entry.
  • Admin credentials (optional toggle, --admin): the Azure Kubernetes Service Cluster Admin Role. Returns cluster-admin client certificates that bypass Azure AD — handy when AAD/RBAC is in the way, but it's cluster-admin, so use sparingly.

Then, in-cluster, your Kubernetes RBAC still applies as usual.

AAD-integrated clusters

If the AKS cluster uses Azure AD integration (no local accounts), the user kubeconfig it hands back authenticates via an exec plugin (kubelogin). k8sight merges that entry; using such a cluster then needs kubelogin on your PATH (or pick admin credentials, which use certs and need no plugin). Clusters with local accounts enabled work with no extra tooling.

How auth works

  • Browser sign-in uses OAuth 2.0 authorization code + PKCE with a loopback redirect and the Azure CLI's public client id 04b07795-8ddb-461a-bbee-02f9e1bf7b46, scope https://management.azure.com/.default offline_access.
  • Cluster discovery calls the ARM REST API (management.azure.com) — list subscriptions, then AKS managed clusters.
  • Import calls listClusterUserCredential (or listClusterAdminCredential with the admin toggle) and merges the returned kubeconfig into ~/.kube/config.
  • No credentials are stored beyond the standard kubeconfig entry; the browser session's refresh token lives only for the sign-in.

Troubleshooting

  • "Help us keep your device secure" / Conditional Access blocks it → use Sign in with browser (not device code) — it carries device compliance. If your org still blocks it, fall back to Use the Azure CLI after az login on a compliant session.
  • No subscriptions / no clusters → the account needs at least Reader on the subscription; confirm you signed in with the right tenant/account (the flow shows an account picker).
  • Cluster imports but kubectl fails with an exec error → it's an AAD cluster needing kubelogin; install it, or re-import with admin credentials.
  • Wrong tenant → sign out of Azure in the browser (or use an incognito window) and retry so you can pick the correct account/tenant.

Google GKE

Connect your GKE clusters — your existing gcloud login, browser sign-in, or a service-account key.

k8sight can import Google GKE clusters three ways:

gcloud credentials No setup

If you've run gcloud auth application-default login, k8sight detects those credentials and lists your clusters with no sign-in step — the common case for GKE developers. Nothing to configure.

Browser sign-in

Authenticate with your own Google account in the system browser. Available when the build ships an OAuth Desktop app client; otherwise use gcloud or a key.

Service-account key

Paste a service-account key JSON. Works with no OAuth client; ideal for CI or orgs that block the browser flow.

Use it

Preferences → Cloud Integrations → Add GKE clusters, or the Add cluster → Google GKE option in the context dropdown.

  1. Choose a method: Use your gcloud credentials (if detected), Sign in with browser, or Use a service-account key.
  2. k8sight discovers your GKE clusters across all accessible projects.
  3. Select clusters → Add → they're merged into your kubeconfig (your current context is left untouched).

Using the clusters needs no gcloud or gke-gcloud-auth-plugin: the bundled gke-token.js mints a fresh access token whenever kubectl / the app authenticates. If you imported via gcloud credentials, signing out of k8sight leaves those clusters working (the helper falls back to your gcloud login).

Permissions you need

The signed-in account needs at least Kubernetes Engine Viewer + Browser (or Viewer) IAM on the projects, and two APIs enabled in those projects:

  • Kubernetes Engine API (container.googleapis.com) — to list clusters
  • Cloud Resource Manager API (cloudresourcemanager.googleapis.com) — to list projects

How auth works

  • gcloud credentials — k8sight reads ~/.config/gcloud/application_default_credentials.json (what gcloud auth application-default login writes), the same authorized_user shape a browser sign-in produces — so there's nothing extra to set up.
  • Browser sign-in uses OAuth 2.0 authorization code + PKCE with a loopback redirect — Google's recommended flow for installed apps.
  • k8sight stores credentials at ~/.config/k8s-manager/gke/credentials.json (mode 600): browser sign-in → { type: 'authorized_user', … }; service-account key → the key JSON.
  • The kubeconfig user runs an exec credential plugin: gke-token.js --credentials <path>, which prints an ExecCredential with a short-lived access token. Clients refresh automatically.
  • Users only ever get the access their own Google IAM allows — the shipped OAuth client is just the app's identity, not an authorization grant.

Troubleshooting

  • "Sign in with browser" isn't shown → this build ships no OAuth client id; use your gcloud credentials (run gcloud auth application-default login) or the service-account key option instead.
  • access_denied / "app isn't verified" → add the account under Test users, or publish the consent screen.
  • invalid_grant / no refresh token → the flow requests access_type=offline&prompt=consent; make sure you approved the consent screen. Remove ~/.config/k8s-manager/gke/credentials.json and retry.
  • No clusters found → confirm the IAM roles above and that both APIs are enabled in those projects.
  • Private clusters → a cluster with no public endpoint can't be reached from a desktop; use its private endpoint over VPN/Connect Gateway, or import via a reachable endpoint.

Local & other clusters

Any kubeconfig context works — Docker Desktop, kind, minikube, on-prem.

k8sight uses your existing kubeconfig, so any context already in ~/.kube/config just shows up — no import step. Switch between them from the context picker or the ⌘K palette. Clusters that authenticate with a client certificate or a static token need no extra tooling; ones that use an exec credential plugin (OIDC/kubelogin, cloud CLIs) need that helper on your PATH.

Local clusters in Docker

Local clusters (Docker Desktop, kind, minikube) listen on 127.0.0.1, which inside a container points at the container itself — so the config loads but the connection fails. Either use the native desktop app / npm start (simplest), or reach the host from the container:

docker run --rm -p 127.0.0.1:8080:3001 \
  --add-host=host.docker.internal:host-gateway \
  -v "$HOME/.kube:/home/node/.kube:ro" \
  praveenraghav/k8s-manager-ui:latest

…and set the context's server: to https://host.docker.internal:<port> with insecure-skip-tls-verify: true.

OIDC / kubelogin clusters

Contexts that authenticate with kubectl oidc-login (kubelogin) work — the Docker image bundles the plugin. Since a container can't open a browser, log in on the host first (kubectl get nodes triggers the browser login and caches a token under ~/.kube/cache/oidc-login/), then mount ~/.kube read-write so kubelogin can refresh from inside the container.

GKE browser sign-in — one-time OAuth setup

For maintainers building their own k8sight — enable browser sign-in.

Most people can skip this. It's only needed if you build k8sight yourself and want browser sign-in on by default. The service-account-key option needs none of this.

Browser sign-in needs a Google OAuth "Desktop app" client. You register one client (in a GCP project you own) and ship it with the app — then every user just signs in. This is exactly how gcloud and other desktop tools work, and Google explicitly treats desktop-app client secrets as non-confidential, so it is safe to embed. Takes ~5 minutes, once per app.

1. Pick or create a GCP project

Use any Google Cloud project you control — it only hosts the OAuth client's identity; it does not need to contain the clusters users connect to. console.cloud.google.com → project picker → New Project.

2. Enable the required APIs

APIs & Services → Library, then enable both:

  • Kubernetes Engine API (container.googleapis.com) — to list clusters
  • Cloud Resource Manager API (cloudresourcemanager.googleapis.com) — to list projects

3. Configure the OAuth consent screen

APIs & Services → OAuth consent screen

  • User type: External (works for any Google account). Internal is fine if everyone is in your Workspace org.
  • Fill in the app name, support email, and developer contact email.
  • Scopes: add https://www.googleapis.com/auth/cloud-platform (or leave default and let the flow request it).
  • Test users: while the consent screen is in Testing, add the Google accounts that will sign in. Publishing to Production removes this limit but may trigger Google's verification review for sensitive scopes.

4. Create the OAuth client

APIs & Services → Credentials → Create credentials → OAuth client ID

  • Application type: Desktop app
  • Name it (e.g. k8sight desktop)
  • Click Create, then copy the Client ID and Client secret.

Desktop-app clients use a loopback redirect (http://127.0.0.1:<random-port>/callback) that k8sight opens automatically — you don't configure redirect URIs.

5. Give it to k8sight at build time

Set the client id and secret as environment variables before building. The build step writes them into the bundled app; they are never committed to git.

export GOOGLE_CLIENT_ID='1234567890-abc.apps.googleusercontent.com'
export GOOGLE_CLIENT_SECRET='GOCSPX-...'

Restart k8sight after building, then use Preferences → Cloud Integrations → Add GKE clusters as described above.

Overview & workloads

A live dashboard and every common resource kind.

The Overview is a live dashboard — node/pod health donuts, workload-by-type charts, and cluster capacity. From the sidebar you browse every common kind: Pods, Deployments, StatefulSets, DaemonSets, ReplicaSets, Jobs, CronJobs, Services, Ingresses, ConfigMaps, Secrets, PVs/PVCs, StorageClasses, RBAC, and more.

  • Live metrics — per-pod CPU/memory from metrics-server, with per-container status boxes.
  • Search & filter by name or namespace; pick one or many namespaces.
  • Cross-links — jump namespace → node → pod → owner in a click.
  • Detail drawer — a slide-in panel with metadata, live metric graphs, conditions, containers, and readable annotations.
  • Right-click / row actions — Details, Edit YAML, Scale, Rollout restart, Delete, and Ask AI.

Nodes shows per-node CPU/memory graphs with capacity thresholds and the pods on each node; Namespaces is a searchable list that filters workloads; Helm lists releases with values and the rendered manifest; Custom Resources is a lazy tree (group → kind → instance) with YAML.

Topology

An interactive map of how your workloads connect.

The Topology view is a pan/zoom graph of Deployment → ReplicaSet → Pod → Service relationships, colour-coded by health. Use it to see at a glance what owns what and where traffic flows, then click any node to open its detail drawer.

ArgoCD

A GitOps dashboard — auto-detected when ArgoCD is installed.

When the ArgoCD CRDs are present, k8sight surfaces a full GitOps dashboard: a fleet-health status bar, summary cards, a "Needs attention" panel, and recent activity — plus Applications, View, ApplicationSets, Projects and Settings → Repositories / Clusters, with an "Open Argo CD UI" link.

The View tab

A Topology-style, pan/zoom resource graph: pick a namespace + application to see the Application and all of its managed resources as an interactive tree (Deployment → ReplicaSet → Pod inferred), colour-coded by sync/health — one screen for tracking a single app.

Sync, refresh & more

  • Sync / Refresh dialog with per-app checkboxes, all / out-of-sync / none presets, prune, and normal/hard refresh.
  • Application drawer: properties, source (clickable repo), destination, sync policy, last operation, resource tree, deploy history and events.
  • Actions: Sync (prune/dry-run/force/replace, two-step confirm), Refresh (normal/hard), roll back to a revision, and Delete (cascade or orphan, two-step confirm).
  • Ask AI → Summarize — hand an Application to the built-in assistant to analyze its sync/health and suggest fixes.

Logs, shell & port-forward

A pro log viewer, a real in-pod terminal, and one-click forwarding.
  • Log viewer — timestamps, per-container or merged "all containers" streams, case-sensitive/regex search with match navigation, line wrap, tail size, and one-click download.
  • Interactive shell — a real TTY into pods (kubectl exec -it streamed over WebSocket to xterm.js).
  • Port forwarding — forward a Service port to localhost (choose a port or get a random one).
  • Multi-tab bottom panel — logs / terminal / YAML tabs open side by side.

Edit & apply

Edit any resource's YAML and apply it, with guarded actions.

Open any resource's YAML, edit it, and apply — with syntax highlighting and validation. Per-row and drawer actions cover Scale, Rollout restart, and Delete, and destructive actions use a two-step confirm. Changes always target the currently selected context.

Built-in AI assistant

A read-only, tool-using debugging session — bring your own LLM.

The built-in assistant is a read-only, tool-using session over live cluster data: it can read logs, events and resource specs to help debug, but it can't change anything. Connect any OpenAI-compatible endpoint (TrueFoundry, OpenAI, Azure OpenAI, LiteLLM, …) in Preferences → AI or via env vars. Secrets are redacted before anything leaves the app.

Right-click a resource (or use the drawer) → Ask AI to hand it to the assistant for a summary, event/log analysis, or fix suggestions.

Docked coding agents

Run your installed CLI agent beside the pod terminal.

k8sight detects Claude Code, GitHub Copilot CLI, Gemini CLI, Codex and opencode on your PATH and opens the one you pick in a panel beside the pod terminal — with the app's current cluster context loaded, so the agent can operate on the cluster you're viewing. Choose your agent under Preferences → External Tools (or a custom command). "Ask AI" actions route to whichever agent you've selected.

MCP server

Let any MCP-compatible agent drive your connected cluster.

k8sight is also an MCP server: it exposes its Kubernetes capabilities as tools so any MCP client (Claude Code, Claude Desktop, Cursor, …) can operate the cluster it's connected to — same kubeconfig, same selected context. It's served over Streamable HTTP at /mcp and over stdio.

Add it to Claude Code:

claude mcp add --transport http k8sight http://localhost:3001/mcp

Read tools are always available; write/destructive tools are off by default — enable them with MCP_ALLOW_WRITE=1 (or the Preferences toggle) only when you want an agent to be able to mutate the cluster.

Security

The local API is locked to your machine.

The API and the /ws/exec shell carry your kubeconfig's full read/write access with no per-request auth, so the backend is locked down to the local machine:

  • Loopback by default — it binds 127.0.0.1, so other hosts on your network can't reach it. Set HOST=0.0.0.0 to expose it deliberately (the Docker image does this so its published port works).
  • Same-origin only — a browser page on another origin can't drive the API or the exec WebSocket (a strict origin check, not permissive CORS). Non-browser MCP clients are unaffected.
  • When exposing it (Docker, or HOST=0.0.0.0), publish to loopback and/or put it behind an authenticating proxy — e.g. -p 127.0.0.1:8080:3001. Add proxy origins via ALLOWED_ORIGINS.

Treat the app like kubectl on your laptop: anyone who can reach its port can act as you on the cluster. Don't expose it to untrusted networks without a proxy.

Configuration

Environment variables.
  • KUBECONFIG — path to kubeconfig (default ~/.kube/config).
  • HOST — interface the backend binds (default 127.0.0.1; the Docker image sets 0.0.0.0).
  • ALLOWED_ORIGINS — extra browser origins allowed to call /api and /mcp, comma-separated (for a reverse proxy).
  • LLM_BASE_URL / LLM_API_KEY / LLM_MODEL — connect the built-in assistant to an OpenAI-compatible endpoint (also settable in Preferences → AI).
  • MCP_ALLOW_WRITE — enable MCP write/destructive tools (default 0, read-only).
  • MCP_API_BASE — API base the stdio MCP bridge targets (default http://127.0.0.1:3001).

The backend listens on port 3001; map it to any host port with Docker (-p <host>:3001).

Troubleshooting

Common connection issues.
  • "Could not connect to the cluster" — the modal names the cause and offers a one-click fix. For an expired cloud sign-in, use the Sign in button (or the copyable command) and retry; k8sight auto-refreshes and reconnects the selected context when it can.
  • EKS: imports but everything is forbidden — your IAM principal isn't mapped to Kubernetes RBAC. Add an EKS access entry or an aws-auth mapping — see AWS EKS.
  • AKS: exec error after import — an AAD cluster needing kubelogin; clusters added through k8sight's browser flow need no kubelogin. See Azure AKS.
  • Local cluster loads but won't connect (in Docker) — the API server is on 127.0.0.1; reach the host or use the desktop app. See Local & other.
  • kubectl version-skew warning — that's your local kubectl vs the cluster, not k8sight. Install a kubectl within one minor of the cluster to silence it.

Still stuck? Open an issue on GitHub.
